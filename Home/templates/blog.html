For a long time my default was: component mounts, effect runs, effect fetches. It reads fine in a tutorial. It falls apart the moment the component can re-render for a reason that has nothing to do with the data it depends on.

The failure mode is always some version of the same story. A dependency array that's almost right. A request that fires twice in development and once in production, so the bug only shows up after deploy. A response that comes back after the user has already navigated away, and updates state on a component that no longer cares.

What the effect was actually doing

Underneath the hook, I was hand-rolling three things every single time: a cache key, a cancellation signal, and a loading state machine. None of those are effect concerns — they're data concerns. Once I named them that way, the fix was obvious: stop writing them inline, and let a loader own them.

// before — the fetch lives inside the component
useEffect(() => {
  let cancelled = false;
  fetchUser(id).then(u => { if (!cancelled) setUser(u); });
  return () => { cancelled = true; };
}, [id]);

Moving the same logic into a route loader or a query hook doesn't remove the underlying problem — it just puts it somewhere that's already solved it correctly: caching by key, de-duping in-flight requests, and cancelling stale ones on the way out.

The bug wasn't in my dependency array. It was in deciding that data-fetching was a side effect of rendering at all.

What actually got simpler

Loading and error states stopped being three separate useState calls scattered per component and became one shape returned from one hook. Race conditions disappeared because the fetching layer already de-dupes by key. And — the part that surprised me — components got easier to test, because "what does this render while loading" no longer depended on timing a fake network response inside an effect.

I still reach for useEffect for what it's actually good at: subscribing to something outside React and cleaning up when the component leaves. Fetching data just isn't that.
